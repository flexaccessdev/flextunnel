- strict no backward compatibility or legacy code path no matter what
- run cargo clippy and test after rust code changes; a `cargo fmt` reformat alone runs neither
- to run the CI workflow's clippy + test steps on all three host platforms against the working tree, use `ci/all.sh` — see `docs/local-ci.md`. Worth doing before a release, or after touching platform-gated code (`flextunnel-desktop`'s macOS/Windows backends), which Linux-only checks never compile. If host is Linux, run linux ci on the same host.
- after touching `flextunnel-ffi`'s unsafe code, run it under Miri: `scripts/miri.sh` on Linux and on macvm. For new unsafe there that stays off the network, add its test to `scripts/miri-tests.txt`.
- Rust is kept as `cargo fmt` formats it under `rustfmt.toml`, and CI checks it.
- For codex only no `cargo fmt` because when it does git diff, it gets stuck after cargo fmt.
- always use uv to run python scripts if needed
- clients and server are expected to be trusted and error detections, for example, duplicate id detections are meant for preventing accidental misconfigurations such as running two clients or servers with the same id.
- the desktop client (`flextunnel-desktop`) stores settings in `profiles.json`, with secrets sealed under a master key held in the system keychain; set `FLEXTUNNEL_DEV_CONFIG=1` (or a file path) to store it as plaintext JSON instead, avoiding the macOS keychain access prompt on every unsigned rebuild. Development only — never set it for a real install (the auth secret key is stored unencrypted). For end-to-end tests (especially on macOS, where the prompt blocks an unattended run) set `FLEXTUNNEL_KEYCHAIN=mock` instead: the real sealed store runs against keyring-core's in-memory keychain, in a separate `mock-profiles.json` emptied each start, so nothing persists between runs and the real keychain/profiles are never touched.
- after rust changes that affect iOS (flextunnel-core or flextunnel-ffi, including the FFI config schema and `ios/flextunnel.h`), run `./build-ios.sh release` to rebuild `libflextunnel.xcframework` into `dist/ios/` (this script no longer writes into `../flextunnel-ios`). The iOS app links via its own Swift package (`../flextunnel-ios/Packages/Flextunnel`), which **defaults to the pinned GitHub release**, so it won't see local changes unless you build the app with `FLEXTUNNEL_LOCAL_XCFRAMEWORK=1` — that links this fresh `dist/ios` build through a committed symlink (set it for both `xcodegen generate` and `xcodebuild`, then clean-rebuild). This is an **extra step only needed when actively working on the iOS app side by side** (and only possible on macOS with Xcode + the iOS Rust targets); otherwise just skip it.
- after rust changes that affect Android (flextunnel-core or flextunnel-ffi, including its JNI surface `crates/flextunnel-ffi/src/android.rs`), type-check it with the android job: `ci/unix/mobile.sh android` (`ci/unix/remote.sh -H macvm run ci/unix/mobile.sh` for iOS + arm64-v8a). The mobile jobs are not in the local `ci/unix/ci.sh`/`ci/all.sh` (they need Xcode, an NDK or macvm, and the mobile apps pin their own release); GitHub's ci.yml and release.yml still build both. Each ABI is built on a host with its own CPU, never cross-arch: `./build-android.sh` on that host, or `ci/unix/remote.sh -H macvm run ./build-android.sh release` + `fetch` for arm64-v8a. The Android app (`../flextunnel-android`) links the pinned release unless built with `FLEXTUNNEL_LOCAL_JNILIBS=1`; its `scripts/run-device.sh` does the build, fetch and install for the device's ABI, and `scripts/e2e.sh` tests it against a throwaway server on debian-vm. Only needed when working on the app side by side.
- the iroh transport layer shared with tunnel-rs and ezvpn — relays and address lookup, the per-relay startup probe, relay auth tokens, relay self-hosting — is documented once in https://github.com/flexaccessdev/flexaccess-iroh/tree/main/docs. Do not duplicate it in this repo; update it there and link to it.
- that shared layer's code — `RelayConfig` and the relay probe, endpoint building (the relays that fail the probe taken out of its relay map), the server's in-place home-relay failover, the endpoint-bound auth transcript, the custom-relay `/healthz` check the status views show — lives in the `flexaccess-iroh` crate (`../flexaccess-iroh`, consumed by git tag). Fix it there, tag a release, and bump the tag here; never re-implement or fork a copy of it in this repo. Only flextunnel-specific pieces (ALPNs, the allowlist hook, the auth context, QUIC tuning, and the client's rebuildable endpoint `ClientEndpoint` — the reconnect loop's escalation, which the crate does not carry) belong in `transport/` and `auth.rs`.
- the transport stack underneath is three forks under the `flexaccessdev` org — iroh (`iroh`, `iroh-base`), noq (`noq`, `noq-proto`, `noq-udp`) and netwatch — on flextunnel's own branches there: `flextunnel-1.5.0` in iroh and in noq, `flextunnel-0.20.2` in net-tools, each named for the upstream release it is based on (clones in `../iroh`, `../noq` and `../net-tools`). They are applied through `[patch.crates-io]` in the root `Cargo.toml` rather than as git dependencies, so that every crate in the graph resolves to them; its comments say what each fork carries. Fix transport-stack bugs on those branches and bump `Cargo.lock` here. They began at the commits of ezvpn's `ezvpn-*` branches in the same repos and are separate from them: a fix that both projects need is cherry-picked from one to the other, and nothing pushed to a `flextunnel-*` branch reaches ezvpn. When upstream releases, rebase onto it as a new branch named for that release.
